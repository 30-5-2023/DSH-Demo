# Agent Note: A2A bridge for Business Agent interoperability

Status: implemented

English | [中文](2026-09-20-a2a-bridge.zh.md)

## Problem

The Business Agent can use in-process and product-specific subagent mechanisms, but another standards-based agent cannot discover or call it through a network protocol. The Business Agent also lacks a model-facing operation that can call an independently deployed agent from an Agent Card URL. Direct integration therefore requires custom code for every remote agent and cannot preserve a remote conversation across calls.

## Decision

The `@deepseek-ai/dsh-business-a2a-bridge` plugin under `business-agent/` exposes one Agent Card and JSON-RPC endpoint for A2A Protocol v1.0 and v0.3. The official SDK compatibility layer translates v0.3 Cards, method names, payloads, stream events, and errors while the bridge retains v1.0 internal types. Both generations support message send, streaming send, Task lookup, and Task cancellation. Each A2A context maps to one durable DSH Session; turns within a context execute serially, while distinct contexts use bounded concurrency. The bridge persists context and Task identity before prompting the Session so retries, cancellation, and Host restart recovery use stable records.

The plugin registers `call_a2a_agent`, which accepts an Agent Card URL, a text or JSON message, and optional local files. The client resolves the Card on every call, allows private HTTP(S) addresses for intranet deployment, enforces timeout, redirect, scheme, response-size, and file-size limits, and returns compact task state, output, and materialized file paths. It does not accept outbound credentials in model-visible input. The separate `publish_a2a_file` tool lets an inbound Task explicitly attach a stable snapshot of a local file to its completing Artifact.

Python `a2a-sdk==0.3.2` file Parts are the supported file wire format. Files at or below the configured inline threshold use `FileWithBytes`; larger files use `FileWithUri` only when a dedicated listener can serve them, while shared-listener mode rejects them with `A2A_FILE_URL_UNAVAILABLE`. Every local, inline, or downloaded file is first stored by the existing DSH attachment service. A separate version-one `a2a_bridge_file_links` storage domain owns only random 256-bit download tokens, Task ownership, attachment references, media types, and expiry. It does not duplicate or delete attachment bytes. Remote output files are materialized through the mounted attachment provider and returned without embedding their bytes in tool results.

Inbound service exposure defaults to a dedicated loopback listener. A deployment can bind that A2A-only listener to `0.0.0.0` without exposing the shared DSH Web listener. The same dedicated listener serves opaque `GET` and `HEAD` file URLs; the shared listener never exposes them, range requests are rejected, and expiry revokes bridge access. The deployment supplies the advertised `publicBaseUrl` at runtime, so container and host addresses do not enter the image and `0.0.0.0` never appears as a client URL. One asynchronous Cordis effect owns repository recovery, listener startup, outbound-tool registration, and cleanup so disposal during startup cannot leave a listener, download stream, or repository active. Bearer authentication remains available through a named environment variable but is optional for the research deployment. Logs and protocol failures omit authorization values, complete prompts, reasoning, tool calls, full remote response bodies, and unnecessary download tokens.

An inbound Session that calls `ask_user_question` suspends inside the live executor while its Task records `input-required` durably. The status Message contains a TextPart plus a DataPart identified by `urn:deepseek-harness:a2a:input-required:v1`. A continuation on the same Task accepts either a DataPart identified by `urn:deepseek-harness:a2a:input-response:v1` with one answer per pending question or a non-empty TextPart for the first question. Invalid answers retain the pending state with a safe diagnostic. A FilePart can accompany the interaction as guidance, but it cannot answer the question. v0.3 clients query the status with `tasks/get`; the bridge does not invent a `message/get` method.

The suspended question is intentionally in memory because the live `ask_user_question` promise and its Session execution stack are not serializable. It retains the context serialization lock and one bounded-concurrency slot until an answer, cancellation, shutdown, or the request deadline; the Bundle default is five minutes. Startup marks an interrupted pending Task failed instead of pretending it can resume. A host-wide question listener uses `global` and `prepend` so it observes scoped questions before the normal UI answerer, but it claims only an exact live Session id with an open A2A Task window and immediately delegates every unrelated request.

For outbound calls, `call_a2a_agent` returns the pending status as `interaction` with its `task_id`, materializes any accompanying FilePart into `files`, and accepts that `task_id` on the next call. The answer therefore continues the same remote Task instead of starting another conversation. Completed, failed, and canceled results omit `interaction` and preserve the existing output and safe-failure fields.

This decision complements the existing [subagent capability](2026-06-21-subagent-capability-seam.md): subagent providers coordinate children selected by local composition, while A2A provides standards-based discovery and invocation between independently deployed agents.

## Alternatives considered

**Implement A2A as another named subagent provider.** This would reuse local delegation vocabulary, but it would hide A2A discovery, Task lookup, streaming, and durable context semantics behind a one-shot child-run abstraction. The bridge instead owns the protocol lifecycle and exposes one explicit outbound tool.

**Expose a bespoke internal HTTP endpoint.** A smaller request/response API would be quicker to implement, but every peer would need a custom adapter and could not use official A2A clients. The bridge uses the official SDK and the A2A v1.0 JSON-RPC binding.

**Expose multiple agents or an in-process registry.** A registry would add routing, naming, and policy questions before the first interoperable path exists. One process advertises one configurable Agent Card; deployments that need distinct agents run distinct compositions.

**Require HTTPS and reject private addresses.** Internet-facing defaults would prevent the requested intranet URL-only deployment and local two-instance tests. The bridge permits private HTTP(S) URLs, rejects embedded credentials and unsafe redirects, and leaves TLS termination to deployment infrastructure.

**Bind the shared Host listener to every interface.** This would make A2A reachable with fewer listener components, but it would also expose the Web UI and unrelated Host routes. The dedicated listener serves only Agent Card discovery and the configured JSON-RPC route.

**Require a reverse proxy for every intranet deployment.** A proxy remains useful for TLS and production policy, but making it mandatory would block the requested direct pre-research path. The runtime listener accepts a deployment-owned public URL and can sit behind a proxy later without changing the image.

**Encode every file inline.** Inline base64 is simple but multiplies JSON body size and forces large files into memory. The configured threshold keeps small files self-contained and moves larger files through a bounded stream and expiring URL.

**Send local filesystem paths over A2A.** A path is meaningful only on the machine that owns it and would disclose filesystem layout without transferring bytes. The bridge resolves paths locally, snapshots them into attachments, and sends only bytes or HTTP URLs.

**Serialize and resume the pending question after restart.** This could release process ownership while the caller decides, but a durable Task record cannot reconstruct the live Session execution stack or arbitrary tool continuation behind `ask_user_question`. The bridge records the protocol state, keeps the real continuation in memory, and fails an interrupted Task on restart.

**Let the normal UI question answerer observe A2A questions first.** This would preserve ordinary listener order, but a UI answerer could claim or queue a question before the A2A caller receives `input-required`. The bridge receives questions first and uses exact Session and Task-window identity to delegate every question it does not own.

## Verification

- The official A2A v1.0 client vertical test discovers the Agent Card and completes synchronous send, streaming send, Task lookup, cancellation, context continuation, and restart recovery against the Loader-composed Business Agent.
- Store and executor tests pin Session reuse, interrupted-Task recovery, duplicate-message idempotence, cancellation races, stream disconnects, malformed content, bounded concurrency, and quiescent teardown.
- Client, file-transfer, and tool tests pin text and JSON results, ordered local-file input, raw and URI output materialization, exact-origin and redirect policy, size thresholds, shared-mode URI rejection, Task-window identity, wrapped upload diagnostics, Card refetching, timeouts, cancellation, and failure cleanup without an outbound authorization input.
- Interaction codec, broker, executor, request-handler, lifecycle, and vertical tests pin schema validation, structured and plain-text answers, invalid-answer republication, exact Session ownership, listener delegation, status visibility through `tasks/get`, same-Task continuation, retained concurrency, timeout, cancellation, shutdown, and restart failure.
- Exact-version interoperability uses Python `a2a-sdk==0.3.2` in both directions and covers input-required continuation, interaction FilePart materialization, `FileWithBytes` at exactly 1 MiB, `FileWithUri` at 1 MiB plus one byte, names, media types, Part order, SHA-256 values, legacy discovery, streaming, lookup, cancellation, and v1.0 non-downgrade. `pwsh -NoProfile -File business-agent/verify-a2a-python-v032.ps1` owns the exact installed-version check; a Windows PowerShell 5.1 regression verifies that missing package metadata reaches installation without a native-command error.
- The `business-a2a-call` recorded Session pins `task_id` in the model-visible input schema, `interaction` in the model-visible tool result, one deterministic input-required response, a structured answer, same-Task completion, durable tool events, and absence of model reasoning and credentials.

## Consequences

Standards-based peers can discover and call the Business Agent without a custom adapter, and the Business Agent can continue a remote A2A conversation or answer its questions with a Card URL, message, optional files, returned context id, and returned Task id. The bridge adds durable Task and file-link records alongside DSH Session turns; branded identifiers, per-context scheduling, durable admission, attachment snapshots, and race coverage prevent unrelated cancellation, duplicate terminal states, mutable file reuse, and stranded restart state.

An input-required wait consumes one configured context slot and cannot survive process loss. This cost keeps the exact Session execution and its question promise alive, while durable Task status lets callers observe the wait and receive an explicit failure after restart rather than an apparently resumable orphan.

Allowing private HTTP endpoints accepts intranet transport risk and server-side request forgery exposure by design. Deployments control which model and users can invoke the tool; the fetch policy still rejects credentials, fragments, non-HTTP schemes, downgrade redirects, unbounded redirects, timeouts, and oversized bodies.

Optional Bearer authentication protects only the inbound JSON-RPC route when configured and does not protect capability-token downloads or provide per-user identity, outbound credentials, mutual TLS, or authorization policy. An unauthenticated wildcard listener accepts any caller that can reach its port, and a disclosed unexpired file URL grants its holder the file bytes. This mode is suitable only for the bounded research environment. Production authorization remains outside this interoperable path.
