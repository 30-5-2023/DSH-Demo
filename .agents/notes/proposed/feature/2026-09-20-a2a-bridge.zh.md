# Agent Note: 用于 Business Agent 互操作的 A2A bridge

Status: proposed

[English](2026-09-20-a2a-bridge.md) | 中文

## 问题

Business Agent 可以使用进程内及特定产品的 subagent 机制，但其他遵循标准的 agent 无法通过网络协议发现或调用它。Business Agent 也缺少一个面向模型的操作，不能通过 Agent Card URL 调用独立部署的 agent。因此，每个远端 agent 都需要定制集成代码，而且多次调用无法延续远端会话。

## 提案

在 `business-agent/` 下增加一个插件，暴露一张 A2A Protocol v1.0 Agent Card 和一个 JSON-RPC 端点。支持 `SendMessage`、`SendStreamingMessage`、`GetTask` 和 `CancelTask`；把每个 A2A context 映射到一个持久化 DSH Session；串行执行同一 context 内的轮次；并允许不同 context 之间进行有界并发。在提示 Session 之前持久化 context 和 Task 身份，使重试、取消和 Host 重启恢复使用稳定记录。

注册一个 `call_a2a_agent` 工具，接收 Agent Card URL 以及文本或 JSON 消息。客户端每次调用都重新解析 Card，允许内网部署使用私有 HTTP(S) 地址，强制执行超时、重定向、协议和响应大小限制，并且只返回紧凑的任务状态与输出。模型可见输入不接受出站凭据。

入站服务默认只暴露在回环地址。监听 `0.0.0.0` 的部署必须显式提供公开基础 URL，并通过具名环境变量提供非空 Bearer token。Agent Card 保持公开以供发现，JSON-RPC 路由则要求 token。日志与协议失败信息不得包含授权值、完整提示词、推理、工具调用或完整远端响应正文。

此决策补充现有的 [subagent 能力](../../implemented/feature/2026-06-21-subagent-capability-seam.zh.md)：subagent 提供方协调由本地组合选择的子 agent，而 A2A 为独立部署的 agent 之间提供基于标准的发现和调用。

## 曾考虑的替代方案

**把 A2A 实现为另一个具名 subagent 提供方。** 这可以复用本地委派词汇，但会把 A2A 发现、Task 查询、流式传输和持久化 context 语义隐藏在一次性子 run 抽象之后。因此 bridge 自行负责协议生命周期，并暴露一个明确的出站工具。

**暴露自定义内部 HTTP 端点。** 更小的请求/响应 API 实现更快，但每个对端都需要定制适配器，而且无法使用官方 A2A 客户端。因此 bridge 使用官方 SDK 和 A2A v1.0 JSON-RPC 绑定。

**暴露多个 agent 或进程内注册表。** 注册表会在第一条可互操作路径出现前引入路由、命名和策略问题。一个进程只声明一张可配置 Agent Card；需要不同 agent 的部署运行不同组合。

**强制 HTTPS 并拒绝私有地址。** 面向公网的默认规则会阻止所需的内网 URL-only 部署和本地双实例测试。bridge 允许私有 HTTP(S) URL，拒绝嵌入凭据和不安全重定向，并把 TLS 终止交给部署基础设施。

## 验收标准

- 官方 A2A v1.0 客户端可以发现 Agent Card，并在真实 Business Agent 组合上完成同步发送、流式发送、Task 查询和取消。
- 每个 A2A context 在多次调用和 Host 重启后复用同一个持久化 DSH Session；恢复时，中断的活动 Task 变为稳定的失败 Task。
- 重复 message id 只创建一个 Task 且只提示 Session 一次，包括同步与流式请求同时重试的情况。
- `call_a2a_agent` 只凭第二个本地 Business Agent 的 Agent Card URL 和消息完成调用，支持文本与 JSON 结果，且不暴露出站授权输入。
- 聚焦测试覆盖取消竞态、流断开、格式错误的内容、重定向与大小限制、有界并发、完全停稳的清理和安全失败摘要。

## 风险

协议 Task 与 DSH Session 轮次具有不同的生命周期和取消语义。错误关联可能取消无关轮次、产生两个终态或在重启后遗留工作；本设计使用品牌化标识符、按 context 调度、持久化准入和显式竞态测试来约束这些失败。

允许私有 HTTP 端点意味着按设计接受内网传输风险和服务端请求伪造风险。部署必须控制哪些模型与用户可以调用该工具，同时 fetch 策略仍必须拒绝凭据、fragment、非 HTTP 协议、降级重定向、无限重定向、超时和过大正文。

Bearer 认证只保护入站 JSON-RPC 路由，不提供按用户身份、出站凭据、双向 TLS 或授权策略。这些能力不属于首个可互操作路径的范围。
