# Agent Note: A2A bridge for Business Agent interoperability

Status: proposed

English | [中文](2026-09-20-a2a-bridge.zh.md)

## Problem

The Business Agent can use in-process and product-specific subagent mechanisms, but another standards-based agent cannot discover or call it through a network protocol. The Business Agent also lacks a model-facing operation that can call an independently deployed agent from an Agent Card URL. Direct integration therefore requires custom code for every remote agent and cannot preserve a remote conversation across calls.

## Proposal

Add one plugin under `business-agent/` that exposes a single A2A Protocol v1.0 Agent Card and JSON-RPC endpoint. Support `SendMessage`, `SendStreamingMessage`, `GetTask`, and `CancelTask`; map each A2A context to one durable DSH Session; serialize turns within a context; and allow bounded concurrency across contexts. Persist context and Task identity before prompting the Session so retries, cancellation, and Host restart recovery have stable records.

Register one `call_a2a_agent` tool that accepts an Agent Card URL and a text or JSON message. The client will resolve the Card on every call, allow private HTTP(S) addresses for intranet deployment, enforce timeout, redirect, scheme, and response-size limits, and return only compact task state and output. It will not accept outbound credentials in model-visible input.

Default inbound service exposure to loopback. A deployment listening on `0.0.0.0` must provide an explicit public base URL and a non-empty Bearer token through a named environment variable. The Agent Card remains public for discovery, while the JSON-RPC route requires the token. Logs and protocol failures must omit authorization values, complete prompts, reasoning, tool calls, and full remote response bodies.

This decision complements the existing [subagent capability](../../implemented/feature/2026-06-21-subagent-capability-seam.md): subagent providers coordinate children selected by local composition, while A2A provides standards-based discovery and invocation between independently deployed agents.

## Alternatives considered

**Implement A2A as another named subagent provider.** This would reuse local delegation vocabulary, but it would hide A2A discovery, Task lookup, streaming, and durable context semantics behind a one-shot child-run abstraction. The bridge instead owns the protocol lifecycle and exposes one explicit outbound tool.

**Expose a bespoke internal HTTP endpoint.** A smaller request/response API would be quicker to implement, but every peer would need a custom adapter and could not use official A2A clients. The bridge uses the official SDK and the A2A v1.0 JSON-RPC binding.

**Expose multiple agents or an in-process registry.** A registry would add routing, naming, and policy questions before the first interoperable path exists. One process advertises one configurable Agent Card; deployments that need distinct agents run distinct compositions.

**Require HTTPS and reject private addresses.** Internet-facing defaults would prevent the requested intranet URL-only deployment and local two-instance tests. The bridge permits private HTTP(S) URLs, rejects embedded credentials and unsafe redirects, and leaves TLS termination to deployment infrastructure.

## Acceptance criteria

- An official A2A v1.0 client discovers the Agent Card and completes synchronous send, streaming send, Task lookup, and cancellation against the real Business Agent composition.
- Each A2A context reuses one durable DSH Session across calls and after a Host restart; interrupted live Tasks become stable failed Tasks after recovery.
- Duplicate message ids create one Task and prompt the Session once, including concurrent synchronous and streaming retries.
- `call_a2a_agent` calls a second local Business Agent with only its Agent Card URL and message, supports text and JSON results, and exposes no outbound authorization input.
- Focused tests cover cancellation races, streaming disconnects, malformed content, redirect and size limits, bounded concurrency, quiescent teardown, and safe failure summaries.

## Risks

Protocol Tasks and DSH Session turns have different lifecycle and cancellation semantics. Incorrect correlation could cancel an unrelated turn, emit two terminal states, or strand work after restart; the design uses branded identifiers, per-context scheduling, durable admission, and explicit race tests to constrain those failures.

Allowing private HTTP endpoints accepts intranet transport risk and server-side request forgery exposure by design. Deployments must control which model and users can invoke the tool, and the fetch policy must still reject credentials, fragments, non-HTTP schemes, downgrade redirects, unbounded redirects, timeouts, and oversized bodies.

Bearer authentication protects only the inbound JSON-RPC route and does not provide per-user identity, outbound credentials, mutual TLS, or authorization policy. Those capabilities remain outside this first interoperable path.
