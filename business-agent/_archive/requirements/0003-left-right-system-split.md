## 当前结论

> **只想快速理解要做什么，看 [../ARCHITECTURE.md](../ARCHITECTURE.md)——那份文件只放图。本文件是决策记录，记录取舍与理由。**

需求方提出：**左侧和右侧可以看成两个不同系统**——今天左侧用 DSH 只是「最简化实现」，后续左侧可能换成别的 agent。这条判断改变了实现的分层方式，本文件把边界画清楚。

结论是：**工单服务是真正的独立服务（自己的包、自己的端口、自己的接口）；今天只是恰好和宿主跑在同一个进程里，换一个配置项就能拆出去。**

> **2026-09-16 后续澄清推翻了下面这张图里的第一条**：需求方明确「业务系统就是工单服务，当前是 mock 的工单服务，相当于实际的业务系统」，所以**没有「连业务系统的 WebSocket 客户端」这一层**，`· 订阅业务系统（WebSocket）` 那一行作废；真实业务系统照本服务已定的三张脸实现即可。本文件后面凡是提到「① 业务系统 → 服务 WebSocket」「两条事件链路」的地方，都按这条读。理由见文末决策记录。

```
┌──────────────────────────────────────────────────────────┐
│  工单服务 workorder-service          ← 与 agent 无关       │
│  · 维护工单/产线状态缓存                                  │
│  · 对外一条中立的事件流 + 一组只读查询                     │
│  · 保存绑定表：客户端标识 ↔ 工单                           │
└───────────┬──────────────────────────────┬───────────────┘
            │ wire（主机中立，HTTP + SSE）   │
     ┌──────┴───────┐              ┌───────┴────────────┐
     ▼              ▼              ▼                    ▼
 右栏看板       事件流消费者      DSH 适配器          别家 agent 适配器
 （渲染层）     （任意客户端）    （今天）             （将来）
```

**三层，各有各的替换理由**：

| 层 | 职责 | 换掉它的理由 | 今天在哪 |
|---|---|---|---|
| 工单服务（**它就是业务系统**，今日是 mock） | 自己就是产线执行引擎、缓存状态、发事件、存绑定 | 业务方提供自己的实现时（引擎不换，换的是「活动怎么真跑」这一次调用） | 同进程，但**不 import DSH** |
| 渲染层（右栏） | 把工单状态画成产线看板 | 换宿主界面时 | DSH 浏览器半插件，**只走 wire 拿数据** |
| agent 适配器 | 把事件变成对话内容、需要人时唤醒、从工具调用里提取绑定 | 换 agent 时 | DSH 宿主半插件 |

## 工具面已经天然可移植

这是本文件最省事的一条：**查询与推进走业务系统的 MCP 工具**（0002 已定），而 MCP 是跨 agent 的标准。所以：

- 换 agent 时，**工具面一行都不用改**——任何支持 MCP 的 agent 都能直接调业务系统。
- 真正要为每个 agent 重写的，只有两件小事：**把事件写成该 agent 的对话内容**，以及**在该 agent 空闲时叫醒它**。

在 DSH 上这两件事分别是 `session.append('user/message', …, {surfaceOp:'append'})` 与 `agent.followup()`（0002 已核实）。在别的 agent 上会有各自的对应物，但都是**几十行的适配器**，不是重新实现一套。

所以「左侧可能换成别的 agent」这件事的成本被高估了：**要重写的只有适配器，服务与右栏都不动。**

## 三条把边界守住的规则

1. **工单服务不 import 任何 DSH 的东西。** 不用 `ctx`、不用 cordis、不用会话类型。它对外的全部能力就是那条 wire。这一条是分治成立的前提——一旦服务里出现 `agent.session`，它就不再是独立系统了。
2. **右栏渲染层只用 wire 拿数据，不读 DSH 的会话状态。** 今天它确实注册在 DSH 的右栏槽位里，但那是「壳」；数据、状态、订阅方式全部走 wire。将来换宿主，换壳不换血肉。
3. **绑定表存在服务里，不存在 DSH 里。** 绑定的语义是「哪个客户端在看哪张工单」，键是一个抽象标识（今天由 DSH 适配器提供会话 id）。绑定**怎么建立**是适配器的事（0002 定的：从 MCP 工具调用里读），绑定**存在哪**是服务的事。

## 一个可执行的检验

分治有没有真正成立，用这条检验：**把 DSH 整个拿掉，工单服务还能不能独立跑起来、右栏的数据还能不能从它的接口上拿到？**

- 能 → 边界是干净的，将来换 agent 只改适配器。
- 不能（例如服务要 `ctx` 才能工作、右栏数据要从会话投影里读）→ 边界是假的，只是文件分了目录。

这条检验要落成 M1 的一条验收标准，不能只写在文档里。**它也是「服务单独成包」的直接理由**：服务可以独立启动、独立 `curl`，检验自然成立。

## 别把「独立进程」当成今天的必答题

需求方同时说「当前 DSH 是为了最简化实现」。所以分治的收益来自**分层纪律 + 服务独立成包**，不来自「今天就有两个进程要管」。下面「今天怎么跑」一节给的 embedded 模式，正是这个平衡点：服务是真的独立服务（自己的包、自己的端口、自己的接口），今天只是**恰好和宿主跑在同一个进程里**。

## 服务长三张脸（方案）

需求方要的是「右侧工单系统有独立服务，和前端靠接口交互，和左侧 agent 靠约定的 MCP 或 WebSocket 交互」。落到设计上就是服务对外暴露三张脸，各有各的消费者。

> **本节画的时候还认为业务系统在服务外面**（下面的 ① 那条边）。后续澄清推翻了它：业务系统就是工单服务本身，今日是 mock；三张脸是**我们定的契约**，真实业务系统照做。下面的 ②③ 与正文其余部分不受影响。见文末决策记录最后两条。

```
   ┌──────────────────────────────────────────┐
   │  工单服务 workorder-service（= 业务系统）  │
   │  执行引擎 · 执行实现 · 事件流 · 绑定表     │
   └──┬────────────────┬──────────────────┬────┘
      │ ① HTTP         │ ② SSE            │ ③ MCP
      ▼                ▼                  ▼
   右栏看板        右栏 + 适配器        左侧 agent 的
   （浏览器）      （同一条流）         工具面
```

### 事件链路：只有**一条**，协议我们定

| | 谁推谁 | 协议 | 谁定 |
|---|---|---|---|
| ①（原设计，已作废） | 业务系统是 WS 服务端、服务是客户端 | ~~WebSocket~~ | ~~你们定~~ |
| ② 服务 → 右栏 / 适配器 | 服务是推送方 | **SSE** | **我们定**，可以挑最省事的 |

**② 选 SSE 而不是 WebSocket**，因为这条链是**单向推送**：浏览器有原生 `EventSource`（自带重连），Node 侧消费一条 HTTP 流也简单，不需要 WebSocket 的双向能力。除非将来服务需要被前端反向调用同一条连接，否则 SSE 更少代码。

### 脸一：给前端的 HTTP + SSE

```
GET  /orders?status=&q=&page=        工单列表
GET  /orders/:orderId                工单详情（含整条产线）
GET  /orders/:orderId/decisions      决策记录
GET  /events?orderId=                SSE：状态变化
GET  /bindings/:clientId             该客户端当前盯的工单
PUT  /bindings/:clientId             绑定 / 改绑（前端切换看哪张走这里）
```

前端**怎么连**有两条路，推荐后者：

| | 直连服务 | 经宿主反代（推荐） |
|---|---|---|
| 地址 | 服务自己的端口 | `/api/workorder/*` 由宿主转发到服务 |
| 跨源 | 跨源，要处理 CORS + 独立鉴权 | **同源**，无 CORS |
| 鉴权 | 服务自己做 | 复用宿主的信任围栏与 cookie（DSH 上就是 `connection.fetch.register`，见 0001） |
| 换宿主 | 前端不用改 | 每个宿主写一遍反代（几十行） |

推荐反代，理由是它把「跨源 + 鉴权」这两件容易做错的事交给了已经做对的那一层。**今天就把服务挂在自己的端口上，反代只是转发**，所以两条路的实现差别只有一处。

### 脸二：给 agent 的 MCP（工具面）

服务自己做一个 MCP server，暴露查询与推进工具：

```
list_orders / get_order / start_order
start_activity / finish_activity / fail_activity / decide
bind_input / retry_activity / resume_activity / skip_activity
```

传输二选一：`stdio`（服务与 agent 同机）或 `streamable-http`（跨机）。

**这张脸的适配成本是零。** DSH 侧只需要在覆盖层加一行 `@deepseek-ai/dsh-mcp-client`，工具就以 `mcp__workorder__*` 出现在模型面前（0002 已核实）。换别的 agent 同样零改动——**MCP 是标准，这是整个方案里最省事的一环**。

两条要跟你们对齐的约定：

- **工具必须立即返回**。「启动工单」返回「已提交」，不等到跑完（0002 已列为硬约定）。跑两小时的活动不能占住一个 turn。
- **工具参数里工单号的字段名要固定**（例如就叫 `orderId`）。适配器要从工具调用参数里读它来建立绑定（见下），字段名飘了就要跟着改配置。

### 脸三：给适配器的 SSE（事件面）

服务不直接和「agent」说话——agent 是一个对话循环，它没有「收 WebSocket」这个能力。**消费者是每个 agent 各自的适配器**，适配器把事件翻译成该 agent 的对话内容与唤醒。

这条设计方向很重要：**服务永远不知道 agent 的存在**。它只负责说「WO-014 的第 3 步从 running 变成 waiting」，至于这句话在 DSH 里变成一条 notice 行、在别的 agent 里变成什么，是适配器的事。

事件载荷要保持主机中立：

```json
{
  "type": "activity.changed",
  "orderId": "WO-014",
  "activityId": "a3",
  "title": "复核财报口径",
  "from": "running",
  "to": "waiting",
  "needsHuman": true,
  "at": "2026-09-16T14:20:00+08:00"
}
```

`needsHuman` 由**服务**判定（它知道活动是不是人工活动、是不是失败了），适配器不用再算一遍——各层只算自己知道的。

## 今天怎么跑：嵌入式还是独立进程

服务的对外接口是 HTTP，所以「服务在哪跑」和「接口长什么样」是两件事：

| 模式 | 服务在哪 | 谁 listen | 适用 |
|---|---|---|---|
| **embedded**（今天） | DSH 宿主进程内 | 服务自己 listen 一个端口 | 最简化，一个进程启动 |
| **external**（目标） | 独立进程 | 同上 | 服务可独立部署、可被多个宿主共用 |

**关键做法：embedded 模式也让服务真的 listen 一个本地端口、适配器真的走 HTTP 去连它**，不要为了省事在进程内直接函数调用。这样两种模式只有「谁 listen」一处差异，代码路径完全一样；将来切 external 就是改一个配置项。

代价只是本机的一次 loopback 往返，换来的是**边界从「靠纪律维持」升级成「靠网络维持」**——这正是 0003 那条「拿掉 DSH 还能不能跑」的检验最便宜的落地方式。

## 目录怎么放

服务是独立系统，就不该和 DSH 插件混在一个包、更不该共享依赖：

```
business-agent/
  workorder-service/            ← 独立服务：自己的 package.json，零 DSH 依赖
    bin/serve.js                独立启动入口（external 模式用它）
    src/business-ws.js          ① 连业务系统的 WebSocket + 断线重连
    src/store.js                状态缓存与事件流
    src/bindings.js             绑定表
    src/http.js                 ② 脸一：HTTP + SSE
    src/mcp.js                  ③ 脸二：MCP server
  plugins/dsh-plugin-workorder/  ← DSH 侧：适配器 + 右栏
    src/adapter/                SSE 消费、会话翻译、唤醒、绑定提取
    src/pane/                   右栏渲染（数据从服务接口拿）
```

这样拆的额外好处：`workorder-service` 可以**单独跑、单独测、单独部署**，不启动 DSH 也能 `curl` 它——那条 M1 检验自动就成立了。

## 一次完整调用长什么样

以「用户说启动工单」为例，看清三张脸各自在什么时候出场：

```
用户 → AI：「启动 WO-014，输入文件是 a.pdf、b.xlsx」
  AI ──③ MCP──▶ 服务：start_order({ orderId:'WO-014', files:[...] })
                 服务 ──① WebSocket──▶ 业务系统：启动产线
                 服务 ◀──① WebSocket─── 业务系统：步骤1 running
  AI ◀──MCP 返回：「已提交，当前 running」          ← 立即返回，不等
                 服务 ──② SSE──▶ 适配器：activity.changed(to=running)
                 适配器 ──▶ 会话里出现一行「▶ 步骤1 已启动」
                 服务 ──② SSE──▶ 右栏：看板同步更新
  …若干分钟后…
                 服务 ◀──① WebSocket─── 业务系统：步骤3 waiting
                 服务 ──② SSE──▶ 适配器：activity.changed(to=waiting, needsHuman=true)
                 适配器 ──▶ 会话里一行进度 + agent.followup() 叫醒 AI
  AI → 用户：「第 3 步等你复核财报口径」
```

**用户只看左右两侧，三张脸都在背后自动跑。** 工具面（MCP）负责「AI 让服务做事」，事件面（SSE）负责「服务告诉两边发生了什么」，前端接口负责「右栏显示什么」。

## 待澄清问题

- [ ] **脸三（服务 → 适配器）用 SSE 还是 WebSocket？**→ 结论：推荐 **SSE**。这条链是单向推送，`EventSource` 自带重连、Node 侧消费也简单；WebSocket 的双向能力这里用不上。除非将来需要同一条连接反向调用。
- [ ] **前端直连服务，还是经宿主反代？**→ 结论：推荐**经宿主反代**（同源、复用宿主的信任围栏与 cookie）。真要做成真·独立服务给多个宿主用，服务自己还得有一套鉴权，那是另一件事。
- [ ] **MCP 传输用 stdio 还是 streamable-http？**→ 结论：待确认。同机用 `stdio` 最省事；但 `stdio` 会洗掉 `*_TOKEN` 一类环境变量（`packages/subprocess/subprocess/src/index.ts:46`），凭据必须在 MCP 的 `config.env` 里显式列出。跨机或凭据走配置文件，就得用 `streamable-http`。
- [ ] **工具参数里工单号的字段名能不能定死叫 `orderId`？**→ 结论：待确认，但**最好定死**。适配器要从工具调用参数里读它来建立绑定，字段名飘了就要跟着改配置。
- [ ] **服务的 `needsHuman` 判定规则由谁维护？**→ 结论：推荐**服务**。它知道活动是不是人工活动、是不是失败了；让每个适配器各自算一遍会漂移。
- [ ] **服务与适配器今天怎么放？**→ 结论：已定**两个目录、两个包**，服务零 DSH 依赖；今天用 embedded 模式跑（服务自己 listen 本地端口，适配器照常走 HTTP）。
- [ ] **`clientId` 用什么？**→ 结论：待确认。DSH 上自然是会话 id，但服务不该知道「会话」这个概念。可能就叫 `clientId: string`，由适配器保证唯一与稳定（会话重启后仍是同一个 id 才谈得上「恢复绑定」）。
- [ ] **一个工单能不能被多个客户端同时盯？**→ 结论：待确认。影响绑定表是一对一还是一对多，也影响事件流是按 `orderId` 订阅还是按 `clientId` 订阅。
- [ ] **将来换 agent 时，谁负责把右栏搬过去？**→ 结论：待确认。如果右栏也要跟着搬（比如搬到新 agent 的侧栏），渲染层就要按「可移植组件」来设计——今天它是 DSH 的 slot 组件，这层壳无法直接复用。
- [ ] **M1 的「拿掉 DSH」检验做到什么程度？**→ 结论：最轻的做法是直接 `curl` 服务的三张脸（不启动 DSH）；因为服务已经是独立包，这件事天然成立。
